1. סקירה

מערכת אינטרקום לרשת מקומית סגורה. שרת Python יחיד מגיש שני דפי HTML סטטיים ומנתב ביניהם אודיו גולמי מעל WebSocket. אין בסיס נתונים, אין תלויות חיצוניות פרט ל-websockets, ואין תהליך בנייה. בעמדות הקצה רץ דפדפן בלבד.

קובץאחריות
server.pyשרת HTTP סטטי (פורט 8000) + שרת WebSocket (פורט 8001), ניהול מצב גלובלי וניתוב פריימי אודיו
client.htmlעמדת קצה: הצטרפות לצוות, לכידת מיקרופון, ניגון ומיקס של דוברים מרובים
manager.htmlלוח בקרה: הפעלת צוותים, שידור כללי, הצטרפות לערוץ צוות, תצוגת מחוברים

כל האודיו עובר דרך השרת — טופולוגיית כוכב, ללא P2P. השרת אינו מפענח, מערבב או ממיר אודיו; הוא מעביר בייטים ומחליט למי.

2. הפרוטוקול

ערוץ WebSocket יחיד נושא שני סוגי פריימים. פריים טקסט הוא JSON של בקרה, פריים בינארי הוא אודיו. ההפרדה נעשית ב-isinstance(message, bytes) בשרת ובבדיקת typeof event.data בדפדפן.

2.2 פריים אודיו

הדפדפן שולח PCM גולמי ללא כותרת. השרת מוסיף מזהה שולח לפני ההעברה, כדי שהמקבל יוכל להפריד בין דוברים ולמקסס אותם:

3. מודל המצב

כל המצב יושב במופע יחיד של State (שורה 30) בזיכרון התהליך. אין התמדה — הפעלה מחדש מאפסת הכול.

broadcast     : bool          # שידור כללי פעיל
active_groups : set[str]      # צוותים שערוץ הפנים שלהם פתוח
joined_group  : str | None    # הצוות שהמפקד מחובר אליו
peers         : dict[int, Peer]

גזירת המצב של הלקוח

status_for() (שורה 70) — הלקוח אינו מחזיק מצב משלו, הוא מקבל אותו מוכן:

תנאימצבמשמעות
broadcastBROADCASTקליטה בלבד, מיקרופון מושתק
group in active_groups
או joined_group == group		ACTIVEמשדר ברציפות
אחרתSTANDBYלא משדר, לא קולט
מצב גלובלי, לא לכל מפקד יותר ממפקד אחד יכול להתחבר, אך כולם חולקים את אותו State ורואים אותו לוח בקרה. פעולה של מפקד אחד משפיעה על השאר מיד. אם נדרשים מפקדים עצמאיים, המצב צריך לעבור להיות פר-מפקד — זה שינוי מבני ולא פרמטר.

4. מטריצת ניתוב האודיו

זהו לב המערכת: audio_targets(sender) (שורה 78). הפונקציה מקבלת את השולח ומחזירה את רשימת המקבלים. כל פריים בינארי עובר דרכה.

מצבשולחמקבלים
broadcast = Trueמפקדכל המחוברים פרט לשולח
לקוחרשימה ריקה — הפריים נזרק
רגילמפקדלקוחות joined_group בלבד; ריק אם לא הצטרף
לקוחחברי הצוות (אם הצוות ב-active_groups) + המפקדים (אם joined_group הוא הצוות שלו)
אכיפה כפולה, בכוונה גם הדפדפן מגביל שליחה (status === "ACTIVE" בלקוח, transmitting() במפקד) וגם השרת מסנן קליטה. הגבלת הדפדפן חוסכת רוחב פס; הסינון בשרת הוא זה שקובע. לקוח ששולח כשאסור לו — הפריים שלו פשוט נזרק.

שים לב לתוצאה הריבועית: בצוות פעיל בן K חברים, כל פריים נכנס משוכפל ל-K−1 יוצאים. תעבורת השרת גדלה כ-K(K-1), ולא ליניארית.

5. server.py

מודל ההרצה

שני מנגנוני מקביליות חיים זה לצד זה:

  • לולאת asyncio — כל תעבורת ה-WebSocket. משימה אחת לכל חיבור, נוצרת על ידי serve().
  • thread נפרד — ThreadingHTTPServer (שורה 203) מגיש את קובצי ה-HTML מ-BASE_DIR. daemon thread, נסגר עם התהליך.

שני העולמות אינם חולקים מצב, ולכן אין צורך בנעילות. QuietHandler קיים רק כדי להשתיק את לוג הגישות.

מחזור חיי חיבור

handler() (שורה 166):

1. יצירת Peer עם id רץ, רישום ב-state.peers
2. שליחת {type:"groups"}                # עוד לפני זיהוי
3. לולאת הודעות:
     bytes -> struct.pack("<I", id) + data -> audio_targets()
     str   -> handle_control()
4. finally: הסרה מ-peers, ואם לא נותרו מפקדים -
            joined_group = None, broadcast = False
5. push_state()

איפוס המצב ביציאת המפקד האחרון הוא הגנה מכוונת: בלעדיו נפילת דפדפן המפקד הייתה משאירה את כל הלקוחות ב-ACTIVE עם מיקרופון פתוח ללא הגבלת זמן.

לחץ חוזר (backpressure) העברת הפריים היא await asyncio.gather(*[t.ws.send(frame) for t in targets]). אם מקבל אחד איטי ומאגר השליחה שלו מתמלא, ה-await מעכב את משימת השולח — כלומר האודיו שלו נעצר לכולם, לא רק למקבל התקוע. תיקון אפשרי: תור פר-מקבל עם השלכת פריימים ישנים במקום המתנה.

תאימות גרסאות

הייבוא מנסה websockets.asyncio.server ונופל חזרה ל-websockets.server. חתימת handler(ws, path=None) מכסה גם את ה-API הישן שהעביר path וגם את החדש שאינו מעביר.

קובץ הצוותים

groups.txt — שם צוות בכל שורה, נוצר עם ברירת מחדל אם חסר. נקרא פעם אחת ב-main(). שינוי דורש הפעלה מחדש של השרת.

6. צינור האודיו בדפדפן

זהה בשני הדפים. שני AudioWorkletProcessor נטענים כ-Blob URL, כדי לשמור על קובץ בודד ללא קבצי לוואי.

getUserMedia → MediaStreamSource → recorder worklet → ws.send()
▼
ws.onmessage → split(4) → player worklet (mix) → destination

recorder

ה-worklet מקבל מנות של 128 דגימות מהמנוע וצובר אותן ל-1024 לפני postMessage. ה-ArrayBuffer מועבר ב-transfer list ולא מועתק. הצומת מחובר ל-GainNode עם gain = 0 אל היעד, כי צומת ללא חיבור יציאה לא מובטח שיעובד.

player

מחזיק Map של תור מנות לכל מזהה שולח. בכל process() נשלפות 128 דגימות מכל תור והן מסוכמות לתוך פס יציאה יחיד, עם clamp ל-±1. זהו המקבילה למיקסר של הגרסה המקורית ב-Python.

כל תור מוגבל ל-12288 דגימות (כ-256ms). בחריגה נזרקות המנות הישנות. זו ההגנה היחידה מפני הצטברות השהיה — אין jitter buffer אדפטיבי ואין תיקון סחיפת שעונים.

מדוע אין אובדן מנות WebSocket רץ מעל TCP, ולכן אין אובדן — אבל יש head-of-line blocking: מנה שנתקעת מעכבת את כל שאחריה. במימוש UDP המקורי התנהגות זו הייתה הפוכה. בפועל, ברשת מקומית תקינה ההבדל אינו מורגש.

התחברות מחדש

ws.onclose מתזמן connectSocket() מחדש כל 2 שניות, ללא הגבלה. ה-AudioContext וההרשאה למיקרופון נוצרים פעם אחת ושורדים ניתוקים — רק ה-socket נבנה מחדש.
